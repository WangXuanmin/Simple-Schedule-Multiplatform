# 云程日历：优化方向与待办清单

整理日期：2026-09-04

适用项目：Simple Schedule Multiplatform（云程日历）

文档状态：部分实施。勾选项表示本轮代码已完成，不自动代表三端实机或云端验收通过；以[优化实施结果](云程日历_优化实施结果.md)中的验证范围为准。

## 1. 目标与范围

优先把已有的多端同步做得正确、可靠、体验一致，再根据实际数据优化性能。保持个人软件的小规模、轻便和低维护成本，不为增加技术栈而引入微服务、Redis 或独立消息队列。

本清单最初基于代码检查与讨论整理。现已完成本地、浏览器及真实 Supabase 测试，版本 RPC 已部署为兼容模式；Web／Windows 已接入，iOS 按用户要求暂缓。下表保留改造前状况用于对照，当前实现及验证范围见优化实施结果。

优先级定义：

- **P0：数据正确性与可靠性。** 防止旧版本静默覆盖、修改遗漏和异常情况下待同步记录丢失。
- **P1：跨端一致的行为与体验。** 统一业务规则、非阻塞交互、同步触发及重试。
- **P2：效率、测量与可维护性。** 降低重复工作，建立量化指标，完善文档。

## 2. 实施前基线（2026-09-04 历史记录）

| 维度 | Windows | iOS | Web/PWA |
| --- | --- | --- | --- |
| 本地存储 | SQLite | SwiftData | IndexedDB |
| 待同步入队时机 | 上传前持久化入队 | 上传失败后入队 | 上传失败后入队 |
| 界面反馈 | 普通新增、编辑不等待云端上传完成 | 先更新本地列表，再尝试上传 | 部分操作等待上传尝试结束后更新列表 |
| 云端写入保护 | 客户端先读取版本，再发起 upsert；不是原子校验 | 直接 upsert | 直接 upsert |
| 拉取后的处理 | 合并云端、本地和待同步快照 | 更新已有任务时比较时间戳 | 返回云端列表并保存到本地，没有相同的三方合并 |
| 实时通知 | 尚未发现与 Web 等价的订阅逻辑 | 尚未发现与 Web 等价的订阅逻辑 | Realtime 通知经 300ms 防抖后触发同步 |

其他边界：

- 共享合并函数包含“删除状态优先、其他情况按更新时间择新”的规则，但不代表所有客户端和服务端都统一执行了该规则。
- Windows 本地任务保存与队列保存是分开的调用，尚不是一次原子事务。
- 当前核心测试有两个案例：保留较新快照、旧快照不复活删除任务；不能等同于完整同步测试体系。
- `apps/api` 目前为预留目录，不应描述为已建成的独立后端服务。

## 3. P0：服务端原子版本校验与冲突反馈

### 当前问题

- 请求到达顺序不等于用户编辑顺序，晚到的旧请求可能覆盖新状态。
- Windows 的“先查询版本，再写入”存在竞争窗口：查询后，其他设备可能已写入更新版本。
- iOS 和 Web 的直接 upsert 缺少等价保护。
- 客户端 `updatedAt` 受设备时钟偏差影响，不适合作为唯一的并发写入依据。

### 待办

- [x] 明确第一版冲突策略：先检测并报告冲突，不静默覆盖；第一版不做字段自动合并。服务端和 Web／Windows 已实现。
- [x] 为任务引入服务端维护的版本号，Web／Windows 提交自己编辑所基于的版本；iOS 接入另列未完成项。
- [x] 建立 Supabase `write_task_v1` 入口，在数据库同一事务中比较基准版本、更新任务并递增版本号。
- [x] 区分新增与更新：任务 ID 已存在时，不把重复新增当成无条件覆盖。
- [x] 返回明确结果：成功、重复请求、冲突或错误；冲突包含当前云端任务／版本。
- [ ] 将三端写入迁移到同一协议，避免旧的直接 upsert 路径绕过校验；配套调整数据库写入权限并保留用户隔离。
- [x] 稳定请求 UUID、基准版本和不可变内容通过服务端回执去重；响应丢失重试不会重复修改。
- [x] Web／Windows 在本地事务中仅确认对应请求，推进后继基准版本并保留后续修改；iOS 新协议待接入。
- [x] Web／Windows 持久化冲突，提供采用云端或另存本地副本；不自动调高冲突版本强行重发。

### 验收标准

- [x] 两个独立 HTTP 请求并发基于同一版本修改，一成功一冲突；真实双设备界面验收另列未完成项。
- [x] 已确认新版本后到达的旧基准请求得到冲突；已确认请求的重放返回原回执，不重新修改。
- [x] 人为调快或调慢设备时间，不绕过 RPC 版本校验。
- [x] 模拟写入成功但响应丢失，重放原请求返回 duplicate，不产生第二次业务变更。
- [ ] 未授权用户不能读取或修改其他账号任务，也不能绕过统一写入规则。

> 服务端版本号解决的是冲突检测，不会自动判断哪次离线编辑更符合用户意图。“保留最后编辑”仍需要明确的业务定义。

> 当前权限仍兼容旧版直接写入，`strict: false`；因此“三端统一入口”和“无法绕过写入规则”尚不能勾选。严格权限在事务测试中验证后回滚，实际切换脚本已准备但未执行。

## 4. P0：本地任务与待同步记录事务化保存

### 当前问题

iOS/Web 上传失败后才入队，应用若在入队前退出，可能保留了本地修改却缺少待上传记录。Windows 虽然上传前入队，但两次本地写入之间仍有异常窗口。

### 待办

- [ ] 统一普通修改流程：同一本地事务保存任务与待同步记录，事务成功后更新界面，再后台上传。
- [x] Windows：将任务表写入与待同步表写入放入同一 SQLite 事务。
- [x] Web：使用同时覆盖任务和待同步记录存储区的 IndexedDB 事务，并以事务完成作为持久化成功依据。
- [x] iOS：让任务修改与待同步记录在同一次 SwiftData 保存中持久化，并明确保存失败的处理。（源码完成；待 Xcode、旧库迁移和真机验证。）
- [ ] 统一记录必要字段：账号、任务 ID、请求标识、基准版本、待上传内容、创建时间、失败信息。
- [x] 应用重启后从持久化记录恢复待同步工作，不依赖内存中的上传任务。（Web 页面重开与 SQLite 文件重开已验证；iOS 待验证。）
- [ ] 新增、编辑、完成、恢复、删除等持久化修改都走统一入口；明确“撤销删除”等尚未提交操作的边界。

### 验收标准

- [ ] 在本地保存、入队、上传、处理确认等阶段注入失败或强制退出，重启后能恢复尚未确认的修改。
- [ ] 本地事务失败时，不出现“任务已修改但没有队列”或“有队列却没有对应修改”的半完成状态。
- [ ] 上传失败不撤销已经持久化的本地修改，并能显示待同步状态。

## 5. P1：统一本地优先交互与同步状态展示

### 当前问题

Web 部分操作虽然先保存本地数据，但仍等待网络请求结束后更新任务列表。用户无法清晰区分“本地保存完成”和“其他设备已经可以看到”。

### 待办

- [x] Web 新增、完成、删除等操作在本地事务成功后返回，不等待网络结果才刷新界面。
- [ ] 三端区分本地保存失败、待同步、同步中、已确认、冲突等状态；界面可以保持简洁，不必展示全部内部细节。
- [x] 仅在云端确认后显示已同步，不能把本地保存成功描述为云端已更新。
- [x] 本地保存失败时给出错误，不把未持久化的修改显示为已保存。
- [ ] 为弱网、断网和服务器长时间无响应设置验证场景。

### 验收标准

- [ ] 断网或网络请求挂起时，普通任务操作不等待网络才能得到本地反馈。
- [ ] 用户能够辨认尚未上传的修改；状态不会因旧请求返回而错误显示为全部同步完成。

## 6. P1：统一冲突、删除与恢复语义

### 待决策事项

- [x] 两端分别修改不同字段：第一版按任务版本检测，保留冲突供选择，不做字段自动合并。
- [x] 两端修改同一字段：显示云端／本地内容，采用云端或另存最新本地草稿。
- [x] 一端删除、另一端编辑：RPC 按基准版本拒绝过期请求，已确认墓碑不能隐式恢复；旧客户端兼容路径仍有例外。
- [ ] 已同步的删除能否恢复？如何区分明确恢复与旧快照误复活？
- [ ] 删除标记保留多久？长期离线设备返回时如何处理已清理的删除信息？

### 待办

- [ ] 编写一份三端共用的冲突规则说明，明确每种操作组合的预期结果。
- [x] 保留同一任务的本地未上传内容，冲突处理期间不直接用云端列表覆盖用户修改。
- [ ] 对齐 Windows、Web、iOS 的实现；可共享规则和测试输入，不要求强行共用一种语言。
- [ ] 使用统一的账号 / 任务 ID 格式及字段含义，减少平台转换差异。
- [ ] 建立覆盖不同客户端组合的测试案例。

### 验收标准

- [ ] 相同初始状态和操作组合，在 Windows–iOS、Windows–Web、iOS–Web 上得到符合统一规则的结果。
- [ ] 不会把明确恢复操作与旧数据导致的任务复活混为一谈。

## 7. P1：统一同步触发、串行调度与失败重试

### 当前问题

启动、实时通知、联网恢复、前台恢复和手动刷新可能重复触发同步；各端入口不同，失败后的恢复能力也不同。

### 待办

- [ ] 按平台能力明确启动、登录、恢复联网、进入前台和手动刷新的行为；不承诺移动端无限后台执行。
- [x] 为每个账号建立统一同步调度入口，避免完整同步流程重叠；同步中收到新请求时，合并为后续一次同步。
- [x] 保证同一任务的上传顺序及确认处理，不让较早请求影响较新的待同步内容。
- [x] 对网络异常和暂时性服务错误采用有上限的退避重试，并提供手动重试入口。
- [ ] 对登录失效执行会话恢复或重新登录提示；参数错误、权限错误与版本冲突不进行无条件重试。
- [ ] 评估原生端实时通知需求；保留常规拉取作为恢复手段，不把通知通道当成完整操作日志。
- [ ] 防止持续通知或自身写入触发无休止的重复同步。

### 验收标准

- [ ] 恢复联网或进入前台后，能够处理此前未完成的上传和拉取。
- [ ] 多个触发条件密集出现时，没有无序重叠的完整同步流程。
- [ ] 暂时性错误可恢复，永久性错误可解释，不陷入无限重试。

## 8. P2：减少重复上传与全量拉取

以下优化应在正确性方案稳定、且测量显示确有必要后开展。

### 待办

- [ ] 合并同一任务尚未发出的修改；为已发出但未确认的版本保留清晰的身份，不能直接丢弃确认关联。
- [ ] 在保证同一任务有序的前提下，对不同任务采用有限并发上传，避免队列积压时全部串行等待。
- [ ] 评估将客户端“查询版本＋写入”合并为一次服务端原子请求后的延迟收益。
- [ ] 测量全量拉取成本；若确有必要，再设计基于可靠服务端游标的增量拉取。
- [ ] 若引入增量同步，同时处理删除信息传播、游标持久化、分页与失败恢复，不能只增加时间过滤条件。
- [ ] 测量 Realtime 300ms 防抖的取舍：重复请求减少多少，单次通知增加多少等待。

### 验收标准

- [ ] 优化前后使用相同任务规模、网络条件和操作序列比较，不用主观感觉代替数据。
- [ ] 请求量或同步耗时有可复现的改善，且不破坏版本、删除、重试和用户隔离规则。

## 10. 性能与运行反馈

### 待测量的三种延迟

| 指标 | 定义 | 主要反映 |
| --- | --- | --- |
| 本地反馈延迟 | 用户操作到当前设备界面显示修改 | 本地持久化和交互体验 |
| 云端确认延迟 | 本地事务完成到收到云端确认 | 排队、网络、服务端处理及重试 |
| 跨端可见延迟 | 云端变更到另一设备显示新状态 | 通知、调度、拉取与渲染 |

### 待办

- [ ] 为操作、请求及确认建立可关联的记录，便于定位卡在哪个环节。
- [ ] 在正常网络、弱网、断网恢复和批量积压等场景采集样本，记录中位数及较慢请求的分布。
- [ ] 跨设备时间测量考虑时钟偏差，不直接相减两个未经校准的设备时间。
- [ ] 记录待同步数量、最久等待时间、重试次数与失败类型；避免日志包含令牌或不必要的用户内容。
- [ ] 有实测结果后再填写性能目标、优化收益和简历数字。

## 12. 建议实施顺序

### 阶段一：先保证数据不会被静默覆盖或遗漏

1. 明确最小冲突协议和服务端版本规则。
2. 实现服务端原子条件写入、重复请求识别及三端接入。
3. 实现三端本地任务与队列的事务化保存。
4. 同步完成乱序、并发、响应丢失和重启恢复测试。

### 阶段二：统一三端体验与业务规则

1. 修正 Web 等待网络后才更新列表的路径。
2. 对齐删除、恢复与冲突处理。
3. 统一同步调度、触发条件、重试和状态展示。
4. 完成三端互操作与必要的真机验收。

### 阶段三：根据数据优化效率

1. 建立延迟与失败观测基线。
2. 按需增加有限并发、请求合并和增量同步。
3. 更新文档与简历，仅记录有证据支撑的结果。
